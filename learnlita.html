Why It Exists

The hard part isn't the learning

Most people don't lack the desire to learn something — they lack a path. Before the first lesson, you have to work out what to study, in what order, and at what depth for your background. Then you have to stay on track, test yourself honestly, and notice when something didn't land. That overhead is where most attempts quietly stall.

Existing platforms hand you content, but not a path shaped around you. A data scientist picking up a new tool needs different framing than an engineer who already knows the basics; a career switcher needs more scaffolding than someone refreshing old knowledge. A fixed curriculum can't bend to any of them.

Learnlita removes that overhead. You describe what you want to learn in plain English — your goal, your background, your pace — and the system does the rest: it builds the plan, writes each lesson for your level, checks your understanding, finds where you struggled, and adapts.

The product's guiding line — “Curiosity is all you need” — is also its design brief. Every decision traces back to one goal: shrink the distance between wanting to learn something and actually learning it.
How It Works

From a goal to a structured course

The experience is a deliberate pipeline. Each step feeds the next, and the system re-personalizes at every stage — not just at sign-up.

The system is a closed loop. A correct quiz answer saves progress and advances to the next lesson. A wrong answer triggers a second AI call that identifies the specific concept that was missed, and the next lesson is regenerated with a targeted clarification section.

Crucially, personalization isn't a one-time setup step. Every lesson is generated with the learner's profile — background, goals, skill level, preferred style — folded into the AI's instructions, so the same topic reads differently for a beginner, a career switcher, or a domain expert.

Learning Modes

Three ways to experience every lesson

Once a lesson is generated, it can be experienced in three formats. All three are produced by the AI and cached after first use, so the expensive generation only ever happens once per topic.

Read

A full written lesson with explanations, worked examples, analogies, and code snippets. Rendered as rich text directly in the browser.

The default mode. The learner's background, goals, and skill level are folded into every generation prompt, so the same topic reads differently for a beginner versus an expert.

Watch

An animated storyboard. The AI breaks the lesson into up to 8 scenes — each with spoken narration and one visual: code block, diagram, comparison table, concept map, or example card. Visuals reveal in sync with the narration.

One concept per scene; visuals timed to the words. Built to reduce cognitive load compared to a wall of text. Narration is synthesized by Google Cloud TTS and played in the browser.

Listen

A two-host podcast conversation — similar to the NotebookLM audio overview. Two hosts discuss the topic in a natural back-and-forth that's easy to absorb while commuting or doing something else.

Under the hood it's modeled as an audio-only storyboard, so it reuses the same TTS pipeline, player, and audio cache as Watch mode — no duplicate infrastructure.

TTS pipeline and audio caching

Both Watch and Listen use the same narration system. Text is synthesized by Google Cloud Chirp3-HD voices — the most natural-sounding voices in the Google Cloud lineup, noticeably more expressive than the older Neural2 or Wavenet families. Chirp3-HD doesn't expose exact SSML timing marks, so sentence start times are estimated at a measured ~17 chars/sec; the player uses these to highlight the current sentence as it plays.

Synthesis is lazy: the first scene is synthesized immediately for a fast first-play experience; the rest are synthesized on demand in the background. All audio is cached in Google Cloud Storage using content-hash keys — if a lesson is regenerated, the key changes and stale audio is never replayed.

Architecture

Two stateless services on Google Cloud Run

The system is split into two independently deployed services. Both run on Google Cloud Run — containerized, stateless, and horizontally scalable. State lives in the database, not in the service. Any instance of the backend can serve any request.

Both services are stateless containers on Cloud Run. JWT tokens carry identity on every request, so any backend instance can handle any call — no sticky sessions, no shared memory. State lives entirely in Cloud SQL.

The backend is fully async Python — important because LLM calls can take several seconds. A synchronous server would block threads waiting for the model response; async handles that concurrency with a single worker. The frontend is Next.js with server-side rendering, giving fast initial loads without sacrificing interactivity.

A SQLite database mirrors the Cloud SQL schema for local development, so the entire system can be run on a laptop without a cloud connection.

Key Decisions

The choices worth explaining

Claude Code wrote most of the code, but the calls that shaped the product were mine: what to optimize for, where to add guardrails, how to keep it cheap and easy to change. Here are the decisions that mattered — and why:

Provider-agnostic LLM layer

The backend uses the OpenAI Python SDK with a configurable base_url. Swapping to a different AI provider is a single environment variable change — no code touched.

Why: LLM pricing and capability shift rapidly. Locking the architecture to one provider would make it expensive to react. The abstraction costs nothing at build time and is worth a lot later.

Profile injected into every prompt

The user's background, goals, skill level, and learning style are serialized as a markdown block and prepended to every LLM system prompt — not just the first one.

Why: Without this, the model has no memory of who it's teaching across API calls. Every lesson call is stateless; the profile re-anchors the model to the user each time.

Adaptive feedback loop

A wrong quiz answer triggers a second LLM call that analyzes the mistake, identifies the specific weak concept, and injects a “Let’s Clarify” section into the next lesson generation.

Why: Most quiz systems tell you the right answer. This one figures out why you got it wrong and closes the gap. The second call is the differentiator.

Learning-style enforcement with retry

Generated course plans are automatically validated against the requested style (spiral, linear, project-based). If the structure drifts, the system retries with a stricter prompt until it conforms.

Why: LLMs don't reliably follow structural constraints on the first try. Relying on the model to self-correct is fragile; programmatic validation + retry is robust.

Stateless auth via JWT

Google OAuth issues a token; the backend exchanges it for a signed JWT (HS256). Every subsequent request carries the JWT — no session store, no sticky routing.

Why: Cloud Run scales by adding instances. A session store shared across instances adds coordination overhead and a failure point. JWT moves that state to the client.

Cost engineering built in from the start

Lessons are cached after first generation. Daily per-user token budgets are enforced. Rate limiting runs per endpoint. Prompts are structured to hit LLM provider cache windows.

Why: A platform that generates multi-step course content on demand burns tokens fast without controls. These aren't afterthoughts — they're in the initial architecture to make the product economically viable.

Platform-context prompt enforcement

Learnlita is read-only — no code execution, no terminal. The system prompt includes explicit rules, and generated content is post-processed to replace phrases like “run this code” with reading-appropriate alternatives before delivery.

Why: LLMs default to interactive teaching styles. Without this, the model routinely tells learners to “open a terminal” or “execute this script” on a platform where they can only read. The enforcement layer is invisible to the user but essential for coherence.

JSON columns for nested course structures

Course content (modules, lessons, quiz questions) is stored in PostgreSQL JSON columns rather than fully normalized tables. Cascading deletes handle cleanup on course removal.

Why: Course content is document-shaped — deeply nested and variable in structure. Normalizing it into relational tables would add complexity with no query benefit; PostgreSQL JSON gives the flexibility of a document store within a relational system.
